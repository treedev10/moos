NAME
    net - connect MOOS to the network

SYNOPSIS
    net up                   connect (picks a driver for you)
    net up firmware | native connect with that kind of driver only
    net status               show the address, card and link
    net cards                list the network cards MOOS can see
    net test                 check name lookup and the internet
    net selftest             check the HTTPS cryptography
    net dns <a.b.c.d>        use another DNS server
    net http <ip> <port> <path>   low-level plain-HTTP test
    net cookies              list the cookies web servers have set
    net cookies clear        forget every cookie
    net loss <percent>       testing: TCP drops that share of segments
    nettest [-k] [-n] [-r START-END] [-p SIZE] <url|@file>
                             time a download, with its SHA-256

DESCRIPTION
    net up finds a network card, waits for the cable link, then uses DHCP
    to get an IP address, a gateway and a DNS server, like any other
    computer on the network. After that, get, apt, clock sync and the
    desktop's Browser can reach the internet.

    net status shows the address, the gateway, the DNS server, which card
    and driver are in use, the MAC address and whether the link is up.

    net cards lists every network card on the PCI buses with its PCI
    address and ID (vendor:device), says whether MOOS has a driver for it,
    and on a UEFI PC whether the firmware offers its own network driver.
    If "net up" fails, start here.

    net test looks up pool.ntp.org and asks it for the time. net selftest
    checks the cryptography used for HTTPS against known answers.

DRIVERS
    MOOS can use a network card in two ways:

    1. The PC firmware's own driver (UEFI PCs only). Firmware that can
       boot from the network carries a driver for the board's Ethernet
       chip. MOOS can borrow it through the UEFI "Simple Network Protocol",
       which makes almost any wired card work - Realtek, Intel, Broadcom,
       and some USB-Ethernet adapters. "net up" tries this first.

    2. MOOS's own drivers, for these chips:
         RealTek RTL8111 / RTL8168 / RTL8169 / RTL810x   (most consumer
                 motherboards; not testable in an emulator - try the
                 firmware driver first on such a PC)
         Intel PRO/1000 (e1000), 8257x, I217 / I218 / I219 (Intel-chipset
                 boards; VirtualBox's and QEMU's "e1000" cards)
         RealTek RTL8139 (QEMU's default card, old PCs)
       These also work when MOOS was started from an old BIOS.

    "net up firmware" or "net up native" forces one kind.

WHEN NO CARD IS FOUND
    - Plug in an Ethernet cable. Wi-Fi is not supported: it would need a
      USB stack (for USB adapters), the Wi-Fi chip's own firmware, the
      802.11 protocol and WPA2 encryption.

    - Run "net cards". If your card is listed with a MOOS driver, "net up"
      should work; if it says "no MOOS driver", use the firmware's driver.

    - To let MOOS use the firmware's driver, start MOOS in UEFI mode and
      turn the firmware's network support on. In the PC's setup screens
      (press Del or F2 at power-on) look for:
          Network Stack            -> Enabled
          (also: IPv4 PXE Support, LAN Option ROM, or "Network Boot")
      and, if it still is not offered, turn off "Fast Boot".
      On an MSI board: Settings > Advanced > Network Stack Configuration.
      Then "net cards" should say the firmware offers a network driver.

MESSAGES
    no supported network card found
        See WHEN NO CARD IS FOUND above.
    no link - is a network cable plugged in?
        The card is working but sees no cable / switch.
    no reply from DHCP
        The cable is in, but nothing gave MOOS an address. Check that the
        network has a router or DHCP server.

IN QEMU
    build.py gives QEMU an RTL8139 card. Set MOOS_NIC to try another:
        set MOOS_NIC=e1000         (or e1000e, virtio-net-pci)
        python build.py uefi

WHAT NEEDS THE NETWORK
    get          downloads web pages and files, over HTTPS (man get)
    apt          installs packages from GitHub over HTTPS (man apt)
    clock sync   gets the real time from the internet (man clock)
    gui          the desktop's Browser

COOKIES
    Web servers set cookies with "Set-Cookie" (to remember a sign-in, a
    choice, a session). MOOS keeps them in memory until it restarts and
    sends the right ones back with every request - from get, apt and the
    Browser alike - as browsers do (RFC 6265):
      - a cookie goes back only to the server that set it (or, with
        Domain=, to that domain and the names under it), and only for
        its Path and the paths below it
      - Secure cookies go only over HTTPS (and only HTTPS may set them)
      - Max-Age=0, a negative Max-Age or an Expires date in the past
        deletes a cookie; others are dropped when their time is up
    At most 64 cookies are kept (then the oldest goes); values longer
    than 1071 characters are cut. "net cookies" lists them (domain, path,
    name, the start of the value, and how long each is kept);
    "net cookies clear" forgets them all.

TESTING THE NETWORK
    nettest <url> downloads a URL the way a video player reads one - with
    the streaming interface, a piece at a time - and prints the status,
    Content-Length, the size, the time, the speed and the SHA-256 of what
    came, so it can be compared with "sha256sum" of the server's copy.
    It follows redirects. Esc stops it.
        -k            do not check the HTTPS certificate (testing only)
        -n            no SHA-256 (times the network alone)
        -r START-END  ask for those bytes only (Range); END may be left
                      out:  -r 1000-  is from byte 1000 to the end
        -p SIZE       POST SIZE bytes of a test pattern instead of a GET
        @file         read the URL from the first line of a file (for
                      URLs longer than a command line)

    net loss <percent> makes TCP throw away that share (0-50) of the
    segments it sends and receives, at random, to test that lost data is
    sent again. "net loss 0" turns it off. Only for testing.

THE NETWORK STACK
    Everything is MOOS's own code: the card drivers, Ethernet and ARP,
    IPv4, UDP, DHCP, DNS, TCP, HTTP/1.1, and TLS 1.3 for HTTPS (X25519,
    AES-128-GCM, SHA-256/384/512, RSA certificate checking).

    TCP (one connection at a time) is made for real, lossy networks:
      - the window it offers is the free room in its 256 KB receive
        buffer (window scaling), with an update when the reader frees
        room; segments that arrive out of order are kept and the missing
        part is asked for again at once (duplicate ACKs, and SACK when
        the server takes it)
      - what MOOS sends is kept until acknowledged and sent again after a
        timeout that adapts to the round-trip time and doubles on each
        retry (8 tries); the same for its FIN; a closed window is probed
      - the SYN is sent up to 4 times; MSS, window-scale and
        SACK-permitted options; a reset is taken only if it is in the
        window
    HTTP/1.1, one request per connection: GET, POST and HEAD; Host,
    User-Agent ("MOOS/1.2"), Range, cookies; chunked replies are decoded,
    interim "100 Continue" replies skipped. Programs read a reply either
    whole (into the download buffer: 512 KB on a BIOS PC, 4 MB on UEFI;
    larger replies are cut) or as a stream of any length (video).
